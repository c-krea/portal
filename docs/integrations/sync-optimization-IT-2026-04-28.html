Optimización del sync Siesa → Supabase

Meta: bajar el tiempo de sync de ~30 min a <2 min, para correr cada 5 minutos en vez de cada 6 horas.
Diagnóstico: la arquitectura está bien (UPSERT con row_hash es correcto). Los problemas son de implementación.

1. UPSERT en lote (cambio principal)

Hoy sync_engine.py hace un SELECT + INSERT/UPDATE por cada fila. Para recaudo (~3.200 filas) son ~6.400 idas y vueltas a Supabase. Postgres soporta INSERT ... ON CONFLICT que procesa miles de filas en una sola consulta. 

from psycopg2.extras import execute_values
from django.db import connection

def bulk_upsert(table, rows, columns, conflict_target, update_columns):
    cols_sql = ", ".join(f'"{c}"' for c in columns)
    update_sql = ", ".join(f'"{c}"=EXCLUDED."{c}"' for c in update_columns)
    sql = f"""
        INSERT INTO siesa_raw."{table}" ({cols_sql}) VALUES %s
        ON CONFLICT {conflict_target}
        DO UPDATE SET {update_sql}, "siesa_synced_at"=now()
        WHERE siesa_raw."{table}".row_hash IS DISTINCT FROM EXCLUDED.row_hash
    """
    with connection.cursor() as cur:
        execute_values(cur, sql, rows, page_size=500)

Ganancia: ~95% menos tiempo (de minutos a segundos por tabla).

2. Desactivar DEBUG

Con DEBUG = True, Django guarda en memoria todas las consultas SQL del proceso. Consume RAM, agrega overhead, y filtra rutas internas en errores. 

# config/settings.py
DEBUG = False

Adicional: mover SECRET_KEY a variable de entorno (.env), no debe estar en el repo.

3. Las 4 tablas en paralelo

Hoy corren secuencialmente: ocupacion → documentos → cartera → recaudo. Son independientes; pueden correr al mismo tiempo. 

from concurrent.futures import ThreadPoolExecutor

def handle(self, *args, **kwargs):
    with ThreadPoolExecutor(max_workers=4) as executor:
        futures = [executor.submit(sync_one, cfg) for cfg in SYNC_CONFIG]
        for f in futures:
            f.result()

Ganancia: ~3× más rápido (el cuello pasa a ser la tabla más lenta, no la suma).

4. Nueva columna row_id_mov en recaudo

Aplicamos hoy en Supabase la migración que agrega row_id_mov BIGINT a siesa_raw.recaudo. Para que se popule en la próxima corrida, agreguen la línea al mapper: 

# data_sync/mappers/recaudo_mapper.py
recaudo_map = {
    # ... líneas existentes ...
    "valor_final": "valor_final",
    "row_id_mov": "row_id_mov",   # ← nueva
}

Es el ID único por movimiento que entrega Siesa. A futuro probablemente lo convirtamos en la clave natural de la tabla, eliminando los problemas con el composite key actual cuando cruce viene en NULL.
