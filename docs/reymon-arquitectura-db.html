01

Resumen Ejecutivo

Este documento describe la arquitectura de base de datos centralizada de Reymon para el desarrollo de múltiples aplicaciones web que comparten la misma infraestructura de datos.

La estrategia consiste en un único proyecto de base de datos en Supabase (PostgreSQL) dividido en schemas separados — uno por aplicación — con aislamiento fuerte entre ellos. Todas las aplicaciones comparten el acceso de lectura a los datos del ERP (Siesa) a través del schema centralizado siesa_raw, sin que ninguna pueda modificar datos de otra.

Principio fundamental: Una sola base de datos. Múltiples aplicaciones completamente aisladas. Un único origen de datos del ERP compartido de forma segura.

03

Proyecto Supabase — Base de Datos Central

Supabase es la plataforma de base de datos que aloja toda la infraestructura. Funciona sobre PostgreSQL (el motor de base de datos más robusto y seguro del mercado) y provee autenticación, API automática, almacenamiento y seguridad por filas (RLS).

04

Schema siesa_raw — Datos Centralizados del ERP

El schema siesa_raw es el núcleo de datos compartidos. IT de Reymon lo configura una sola vez. Desde allí, cada aplicación extrae la información del ERP que necesita, sin que ninguna pueda modificarla.

Siesa ERP  ──►  siesa_raw  ──►  v2 (C-Krea lee cartera, ocupacion...)
    ▲              (solo         ──►  app_reymon (lee lo que necesita)
    │              lectura)      ──►  app_X (lee lo que necesita)
IT Reymon
(sync cada ~3h)

Tablas Disponibles en siesa_raw

TablaContenido
ocupacionContratos y ocupación de locales
carteraSaldos de cartera por inquilino
documentosFacturas y documentos (últimos 4 meses)
recaudoPagos recibidos
estado_opEstado operativo
estado_resultadosEstado de resultados financieros
sync_batchesRegistro de sincronizaciones del ERP

Reglas de siesa_raw

Prohibido: Ninguna aplicación ni equipo puede hacer INSERT, UPDATE o DELETE sobre siesa_raw. Solo el proceso de sincronización del ERP (rol siesa_sync) puede escribir en este schema.
Seguro: Agregar nuevas tablas a siesa_raw no afecta las apps existentes. Solo operaciones destructivas (DROP, RENAME) requieren coordinación previa.
05

Modelo de Aislamiento por Aplicación

Cada aplicación vive en su propio schema dentro del mismo proyecto. El aislamiento opera en dos niveles: nivel de base de datos (el servidor rechaza accesos no autorizados) y nivel de políticas RLS (cada fila verifica quién puede verla).

¿Qué puede hacer cada aplicación?

OperaciónSchema propiosiesa_rawSchema de otra app
Leer datos (SELECT)✓ Permitido✓ Permitido✗ Bloqueado
Insertar datos (INSERT)✓ Permitido✗ Bloqueado✗ Bloqueado
Modificar datos (UPDATE)✓ Permitido✗ Bloqueado✗ Bloqueado
Eliminar datos (DELETE)✓ Permitido✗ Bloqueado✗ Bloqueado
Crear/modificar tablas (DDL)✓ Permitido✗ Bloqueado✗ Bloqueado
Importante: El bloqueo opera a nivel del servidor de base de datos — no es una restricción de software que se pueda evitar. Incluso si Claude Code intenta acceder a otro schema, el servidor lo rechaza con error de permisos.

SQL de Creación por App (plantilla)

-- Reemplazar 'nombre_app' con el nombre real del schema

-- 1. Crear schema
CREATE SCHEMA IF NOT EXISTS nombre_app;

-- 2. Crear rol de acceso con contraseña
CREATE ROLE nombre_app_dev LOGIN PASSWORD 'PasswordSeguro123';
GRANT CONNECT ON DATABASE postgres TO nombre_app_dev;

-- 3. Acceso completo a su propio schema
GRANT USAGE, CREATE ON SCHEMA nombre_app TO nombre_app_dev;
GRANT ALL PRIVILEGES ON ALL TABLES IN SCHEMA nombre_app TO nombre_app_dev;
GRANT ALL PRIVILEGES ON ALL SEQUENCES IN SCHEMA nombre_app TO nombre_app_dev;
ALTER DEFAULT PRIVILEGES IN SCHEMA nombre_app
  GRANT ALL ON TABLES TO nombre_app_dev;

-- 4. Acceso de solo lectura a siesa_raw
GRANT USAGE ON SCHEMA siesa_raw TO nombre_app_dev;
GRANT SELECT ON ALL TABLES IN SCHEMA siesa_raw TO nombre_app_dev;
ALTER DEFAULT PRIVILEGES IN SCHEMA siesa_raw
  GRANT SELECT ON TABLES TO nombre_app_dev;

-- 5. Permitir visualización directa (DbGate)
ALTER ROLE nombre_app_dev BYPASSRLS;

-- 6. Bloqueo explícito de schemas protegidos
REVOKE ALL ON SCHEMA v2 FROM nombre_app_dev;
REVOKE ALL ON SCHEMA siesa_raw FROM nombre_app_dev; -- solo tenía lectura
06

Autenticación y Control de Acceso

Todas las aplicaciones comparten el mismo sistema de autenticación de Supabase (auth.users). Sin embargo, el acceso a los datos de cada app está controlado por una tabla de perfiles propia en cada schema.

auth.users  (compartido — solo guarda email + contraseña)
     │
     ├──► v2.perfiles          → usuarios de C-Krea
     ├──► app_reymon.perfiles  → usuarios de app Reymon
     └──► app_X.perfiles       → usuarios de app X

Un usuario solo ve datos de las apps donde tiene perfil.

Flujo de Autenticación por App

1

Usuario ingresa a la URL de su app

Cada app tiene su propio dominio en Vercel (ej: portal-ckrea.vercel.app, admin-reymon.vercel.app)

2

Ingresa email y contraseña

Supabase auth verifica la identidad — compartido entre todas las apps

3

La app verifica el perfil

Busca al usuario en su tabla de perfiles propia. Si no existe → sin acceso a datos

4

RLS filtra automáticamente

Cada consulta solo devuelve datos autorizados para ese usuario en esa app

Tabla de Perfiles — Estructura Mínima por App

CREATE TABLE nombre_app.perfiles (
  id          uuid PRIMARY KEY REFERENCES auth.users(id),
  rol         text NOT NULL DEFAULT 'visor'
                   CHECK (rol IN ('admin', 'editor', 'visor')),
  activo      boolean NOT NULL DEFAULT true,
  created_at  timestamptz NOT NULL DEFAULT now()
);

ALTER TABLE nombre_app.perfiles ENABLE ROW LEVEL SECURITY;

-- Solo el propio usuario puede ver su perfil
CREATE POLICY "usuario ve su perfil"
  ON nombre_app.perfiles FOR SELECT
  USING (id = auth.uid());

-- Solo admins pueden crear usuarios
CREATE POLICY "admin crea perfiles"
  ON nombre_app.perfiles FOR INSERT
  WITH CHECK (
    EXISTS (
      SELECT 1 FROM nombre_app.perfiles
      WHERE id = auth.uid() AND rol = 'admin'
    )
  );
07

Roles de Base de Datos

Los roles de base de datos son usuarios de PostgreSQL con permisos específicos. Son independientes de los usuarios de autenticación (Supabase auth). Se usan para que herramientas como Claude Code y DbGate se conecten de forma segura y limitada.

Roles del Sistema

RolAccesoUsoQuién lo tiene
postgres Total Administración del proyecto completo Solo propietario
service_role Total (bypasa RLS) Backend de cada app en producción Solo propietario
siesa_sync Solo siesa_raw Sincronización ERP → DB IT Reymon
ckrea_viewer v2 + siesa_raw (lectura) Visualización en DbGate — C-Krea Equipo C-Krea
nombre_app_dev Su schema + siesa_raw (lectura) Desarrollo con Claude Code y DbGate Equipo de cada app
authenticated Según RLS Usuarios finales logueados en la app Todos los usuarios
Regla de oro: service_role y la contraseña de postgres nunca se comparten con equipos externos. Cada equipo solo recibe las credenciales de su rol limitado.

Proceso de Incorporación — Nueva Aplicación

Este es el proceso estándar para agregar una nueva aplicación al ecosistema. Completar en orden.

Responsabilidades

#TareaResponsable
1 Crear cuenta GitHub y repositorio del proyecto Equipo App
2 Invitar al propietario como colaborador Admin en GitHub Equipo App
3 Crear cuenta Vercel y conectar al repositorio GitHub Equipo App
4 Ejecutar SQL de creación de schema y rol en Supabase Propietario DB
5 Exponer nuevo schema en Supabase → Settings → API Propietario DB
6 Entregar las 3 credenciales al equipo Propietario DB
7 Configurar DbGate con DATABASE_URL del rol limitado Equipo App
8 Agregar credenciales a .env.local del proyecto Equipo App
9 Iniciar desarrollo con Claude Code Equipo App

Las 3 Credenciales que Recibe Cada Equipo

# Archivo .env.local del proyecto

# 1. URL del proyecto Supabase (pública, igual para todos)
NEXT_PUBLIC_SUPABASE_URL=https://[project-ref].supabase.co

# 2. Llave pública Supabase (pública, igual para todos)
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJ...

# 3. Conexión directa limitada (SOLO su schema + siesa_raw)
DATABASE_URL=postgresql://nombre_app_dev.bosylehvmtwtqkrlievy:PASSWORD@aws-1-us-east-1.pooler.supabase.com:6543/postgres
No compartir: SUPABASE_SERVICE_ROLE_KEY y la contraseña de postgres nunca forman parte de las credenciales entregadas a equipos.

Checklist de Verificación

  • El equipo puede conectarse a DbGate y ver solo su schema y siesa_raw
  • Intentar escribir en siesa_raw desde DbGate devuelve error de permisos
  • Intentar acceder al schema v2 desde su conexión devuelve error de permisos
  • El equipo puede crear tablas en su propio schema sin problemas
  • El sistema de login de la app funciona correctamente
  • Los datos de siesa_raw se leen correctamente desde la app

Configuración del Cliente Supabase por App

El cliente de cada app debe estar bloqueado a su propio schema:

// src/lib/supabase/client.ts
import { createBrowserClient } from '@supabase/ssr'

export function createClient() {
  return createBrowserClient(
    process.env.NEXT_PUBLIC_SUPABASE_URL!,
    process.env.NEXT_PUBLIC_SUPABASE_ANON_KEY!,
    {
      db: { schema: 'nombre_app' } // ← bloqueado a su schema
    }
  )
}

Reglas de Seguridad

Reglas Absolutas

ReglaMotivo
❌ Nunca compartir SUPABASE_SERVICE_ROLE_KEY Bypasa toda seguridad — acceso total a toda la DB
❌ Nunca agregar equipos externos al dashboard Supabase El SQL Editor del dashboard tiene acceso de superusuario
❌ Nunca hacer DROP o RENAME en siesa_raw sin autorización Rompe todas las apps que leen esas tablas
✅ Cada equipo solo recibe sus 3 credenciales limitadas Aislamiento garantizado a nivel de servidor
✅ RLS habilitado en todas las tablas de todos los schemas Protección adicional a nivel de fila de datos
✅ Resetear contraseña de rol si un equipo sale del proyecto Invalidar acceso inmediatamente

Qué pasa si un equipo intenta acceder a datos de otra app

El servidor PostgreSQL rechaza la consulta con error permission denied for schema v2. No se devuelven datos parciales. No es posible ver ni un solo registro de otro schema.

Gestión de Accesos

  • El propietario crea y destruye roles de base de datos
  • Cambiar contraseña de un rol no afecta a ningún otro rol
  • Si un desarrollador deja el proyecto: ALTER ROLE nombre_rol PASSWORD 'nueva';
  • Para revocar acceso completo: REVOKE CONNECT ON DATABASE postgres FROM nombre_rol;

Glosario de Términos

TérminoDefinición en lenguaje simple
SupabasePlataforma que aloja la base de datos en la nube. Como el edificio donde viven todos los datos.
PostgreSQLEl motor de base de datos dentro de Supabase. El idioma que habla la base de datos.
SchemaUn piso separado dentro del edificio de datos. Cada app tiene su propio piso.
RLS (Row Level Security)Reglas que deciden qué filas de datos puede ver cada usuario. La lista de invitados por piso.
Rol de DBUn usuario de la base de datos con permisos específicos. Como una llave que solo abre ciertas puertas.
service_roleLa llave maestra que abre todo. Solo para el propietario.
siesa_rawEl schema donde viven los datos del ERP Siesa. El archivo central de información.
ERPSistema de gestión empresarial (en este caso, Siesa). La fuente oficial de datos de negocio.
DbGateHerramienta visual gratuita para explorar la base de datos. Como un explorador de archivos pero para datos.
VercelPlataforma que publica la app en internet automáticamente al subir cambios al código.
GitHubRepositorio del código fuente. Historial de todos los cambios del proyecto.
Claude CodeAsistente de IA que escribe el código de la aplicación basándose en instrucciones en lenguaje natural.
Next.jsFramework de desarrollo web usado para construir las aplicaciones.
Migration / MigraciónUn cambio estructural a la base de datos (crear tabla, agregar columna) registrado como archivo de código.
BYPASSRLSPermiso especial para saltarse las reglas RLS. Solo para roles de visualización directa (DbGate).
